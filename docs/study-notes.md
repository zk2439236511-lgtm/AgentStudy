#### 一、传统开发模式与全栈智驾模式的对比

传统开发模式：死磕语法细节、手写大量CRUD（增删改查）、重复性工作多效率低

全栈智驾模式：由AI来实现我们所想要的步骤、效率提高（减少大量的重复的CRUD以及测试等工作）

经过对比得到结论：在现在AI盛行的时代，开发者最应该具备的是系统架构设计能力，而非以前的代码语法等。

# 第一课  兵马未动，利器先行

#### 一、放弃传统开发模式，使用现在的AI的原因

​	传统开发模式中，发生报错或者查看文档时，每次都需要复制到AI网页端询问，而新模式当中AI直接驻扎在你的本地项目文件当中，能够随时随地的使用，不用复制。



#### 二、如何向AI正确提问

​	要精确的表达自己的意图，而不是粗略广义的提问。例如：**能否帮我编写一个网页**。这样的提问是错误的，没有重心，AI贼会到处是重心，最终导致没有重心。正确的提问应该是：**作为编写前端网页的程序员，请帮我编写一个HTML网页，实现番茄钟的功能。不要使用任何npm库，我最终想看到的是一个黑暗风格、居中显示的现代化UI卡片**。当你用多个条件慢慢引导AI走在正确的道路上，AI所反馈给你的才会更符合你想要的结果。



#### 三、AI并非无所不能

​	我们要做的是如何正确的利用AI，而不是让AI代替我们。首先，我们需要让AI一步步达到我们所预期的结果，而不是一步到位。例如让AI做一个app，我们应该让AI写什么功能，写什么页面，从而一步步搭建起这个app，而不是直接让AI编写一个app。其次，AI的回答不一定百分百正确，仍需要我们人为判断。





# 第二课  **用 AI 做需求分析与架构设计**

#### 一、代码不应该是先进行的步骤

​	项目进行的第一步永远都不是代码，而是需求！就如同建房没有图纸，最终就会坍塌。

​	对AI进行关于需求的描述越简单，那么AI回答的自由度就越高，越不容易找到重点，所以可以让AI向我们提问，我们根据AI的提问再来进行补全和优化。





# 第三课  **后端基石与轻量级数据库**

#### 一、端口爆出Address alreday in use和AI欺骗代码写通的原因

​	缺乏物理隔离自检流程



#### 二、后端两大致命绝交锁

1.CORS跨域黑恶拦截（写完接口先加上CROS）

​	当前后端端口不一致（例如前端运行在 5173，后端运行在 8000），浏览器出于安全规则会无条件阻止前端载入后端数据，报错 CORS Error。

2.SQLite Database Concurrency Lock（锁库异常）

​	SQLite 是把所有数据写入单进程本地文件的，在多核异步读取写入时会因为写入独占锁，报错「database is locked」。





# 第四课  **前端门面与 React 交互美化**

#### 一、前端页面编写的变化

​	旧时代的前端页面是在一个白板上编写，修改一个区域的某个模块便会牵一发动全身影响其他模块，而现在的前端分为多个组件区域，之间互不影响，只需要修改自己组件里面的问题就可以。



#### 二、进阶UI纪律（反馈纪律）

​	1.AI请求组件时，容易出现现象：页面网络延迟或接口报错时直接白屏或者停滞。我们需要让AI在请求组件时，必须要有Loading（骨架屏或者旋转态）以及完整的Error Catch UI交互。

​	2.AI每次重写样式时，会把CSS类名修改，导致自动化测试抓取失败，所以想出了data-testid（例如data-testid="prompt-submit"）。它不参与样式、独立的物理交互属性。



#### 三、如何向AI提供“高品位”审美反馈

​	1.拒绝含糊词汇，给AI提供详细的CSS数值

例如：这个页面太丑了，帮我修改的具有现代感一点。属于无效反馈，AI容易自由发挥，跑偏。下面是正确的提问：

“请增加卡片的内部 padding 到 2rem；为文本输入框添加聚焦 (focus) 时的蓝色微光阴影 (box-shadow: 0 0 10px rgba(6,182,212,0.2))；且整体主背景色改为暗沉磨砂黑 (#090D15)，提升微光品质感。”



​	2.将动画效果拆解为具体CSS动画与状态逻辑

例如：帮我把加载动画直接加上去，要炫酷的！无效反馈，AI容易自由发挥，跑偏。下面是正确的提问：

当 isLoading 状态为真时，用纯 CSS 在按钮头部添加一个宽高为 14px、边框为 2px 且顶部透明的 border-t-transparent 的转圈 Spinner，并将按钮置灰 (disabled) 且改变鼠标状态 (cursor: not-allowed)。





# 第五课  **前后端全链路打通与 SSE 流**

#### 一、大模型应用必须采用流式（Streaming）响应的原因

​	传统REST API通信采用一问一答机制，前端提交数个表单后，后端处理完成一下子全部输出给用户，用户需要等待漫长时间并且对于结果的理解效率很低。而流式通信则逐步将回答输出给用户，极大的减少了用户的等待时间以及提高了用户对输出结果的理解效率。



#### 二、联调试验区避雷点

​	1.联调前置探测原则

​	盲目法指令（×）：AI，帮我把刚才编写的React App.jsx全部对接刚才的流式接口，直接跑通大模型聊天功能。

​	闭环发令（√）：请现在终端执行 curl -s http://localhost:8000/api/health 探测系统，确认握手回传 status=ok 后，再在 App.tsx 写入 Fetch 异步追加更新机制。

​	总结：AI不可能一次盲写跨语言的全栈体系，应该先通过终端探测确认后端API通畅并能够获取数据，再进行前端接口装载。

​	2.并发连接挂断常态

​	盲目法指令（×）：点击按钮就发 fetch 请求，直接 map 出来。

​	闭环发令（√）：请为 fetch 接入 `new AbortController()` 的 signal 控制，当用户重复在输入框点击时，先执行 `controller.abort()` 释放上一个 pending 的过期 SSE 连接。

​	总结：如果不挂载 Abort 信号检测，网络卡顿时用户疯狂双击提交，浏览器将在后台同时创建数千个未终结的 EventStream，彻底撑满系统连接池，产生服务器过载瘫痪。





# 第六课  **可验证的开发闭环**

#### 一、传统Debug方式在AI开发时代效率极低的原因

​	1.抛弃瞎猜，提供完整物理日志

​	必须将完整的错误日志，报错行号等等信息全部复制给AI，而不是提问AI，这里报错了，帮我修改一下。

​	2.闭环验证，坚决不信假成功

​	当AI输出”我已经全部帮你修改好了“，不要完全相信，必须自己亲自运行验证是通过的才可以。



#### 二、开发防止崩溃的核心防线

​	1.防止死循环机制（Anti-Loop）

​	AI 有时会陷入盲目乱改后产生新错接着捂脸瞎猜从而导致错得更深的死循环。如果连续 2 次运行测试失败，必须手动/发指令中断 ，强制让其重新列出核心假设并检查配置，避免 Token 瞬间烧空。

​	2.打开Logger“开眼天眼法”

​	有时代码明明没有报错，但输出结果就是不正确，而此时AI也无法得知内部运作。那么就需要写入（console.log/logger.info），再把输出的日志结果喂给AI。

​	3.物理垃圾清场规则

​	在调试、挂载测试脚本时，AI 往往会在根路径生成 dummy.json / database_test.db 以及未杀除的僵尸测试服务。当程序运行结束时，必须强制执行杀除后台遗留进程命令，保持开发环境纯净。



#### 三、AI代码诊断避坑

​	1.贯彻外科微创手术原则

​	让AI修改时，必须准确控制AI修改的范围，这样才能避免大刀阔斧的修改让原本能运行的功能挂掉。

​	2.闭环必须铁律，物理清理战场

​	每次对话完成后，都需要删除临时文件释放资源。





# 第七课  **代码重构与自动文档**

#### 一、AI代码重构的注意事项

​	1.功能冻结拆分，杜绝边改边加

​	在重构代码的过程中突然心血来潮写两个新功能，一旦报错就搞不清是重构切片隔断带来的，还是新写的功能本身的业务逻辑bug。

​	2.利用自动化测试网，一测到底

​	重构后的第一件事情就是运行回归测试网，检查重构后的功能是否依然正确跑通。



#### 二、重构防崩溃核心

​	1.小步快跑（Incremental Split）

​	绝对不推荐一下子把前后端多个文件全部重构，推荐按照：App.tsx—>重构验证—>main.py—>重构验证。确保每个关键节点都有物理回执

​	2.高逼格一键文档（Auto README）

​	AI大模型能够利用API描述一键生成高水平、贴图带流程的代码等等的架构文档，让项目拥有大厂级别的华丽质感。

​	3.Git 双向备份护航规则

​	在运行大模型重构前，必须在本地利用Git执行一次，这样能够确保无论发生什么，可以及时回退。





# 第八课  **版本控制与毕业复盘**

#### 一、在AI开发时代，Git指令格外重要的原因

​	1.容错底盘：将Git是作为存档大法

​	AI并非万能的，有时它给你的改动会出现各种原因而崩溃，所以需要利用Git在本地运行存档，之后无论发生什么都可以回退到该存档版本。

​	2.自动书记官：让AI生成高逼格规范Commit

​	不要总是写干枯枯的update或fix。让 AI 辅助阅读你的 `git diff` 物理暂存差异，自动遵循 Angular Commit 规范输出清晰详尽中英对照的提交信息，彰显极致大厂开发者素养。



#### 二、AI结合与自我进化记忆环

​	AI会由于静态无记忆上下文而重复犯错，所以需要我们把犯错经验持续反馈到本地约束文档，这样AI就会吸取教训，避免重复犯错。

​	三部曲：

​	1.踩坑触发(Issue Encountered)

​	在快速开发或部署中，遇到跨域、环境变量或 HMR 崩溃问题，由 AI 与你协同排修通过。

​	2.提炼并写入核心约束(Formulate Regulation)

​	不要让教训溜走。要求大模型把 bug 背景与防范技巧转化为严格规则，加入项目本地 Rules。

​	3.物理沉淀长期记忆(Commit to AGENT_RULES.md)

​	将约束写入 docs/5_AGENT_RULES.md。下次大修或重新起步时，AI 会先读取规则，避免再犯。



#### 三、AI开发与终局部署指南

​	1.宁可百次Commit，绝不裸跑大修

​	物理 Commit 是唯一的时间回溯点。大动刀前、回归测试全绿后、功能抽取完成时，都要保持存档习惯。

​	2.客户端零泄密保卫，仅后端代理与 env 隔离

​	敏感环境变量或 API key 绝不要暴露在浏览器客户端可见作用域，更不能随 Git 裸提交进公共仓库。





# 第九课  **AI 结对编程 10 日精华**

#### 一、驾驭AI结对编程的四大黄金法则

​	1.上下文（Context）是第一生产力

​	当AI突然胡言乱语时，原因就是忘记了前置代码或者条件。

​	2.物理验证，打破假成功的幻觉

​	AI一切的已完成，已修改，已修复等等回答，必须通过命令，运行日志验证是否真的如AI所说。

​	3.步步为营，拒绝一次性大跃进

​	不能够将整个庞大需求一次性全部喂给AI，每次只做最纯粹的一小步，逐步建立反馈环，该功能完成后，才能开启下一个功能

​	4.永远对环境级大改与危险破坏指令喊停

​	当AI多次修改产生类型死锁和配置混乱时，AI就会变得混乱，所以看到环境强制降级或者rm -rf指令时，立刻按下Ctrl+ C 强制拦截！

先弄清原理：向量库本质是一张"内容地图"，把每块文字算成一串坐标存起来。内存版（InMemoryVectorStore）这张地图只画在运行时内存里，进程结束就蒸发，下次启动得把 52 块重新算一遍坐标（花钱花时间）。持久化就是**把算好的地图存成磁盘文件**，下次直接读文件，不再重算。配套还要解决"哪些文件已经算过"——用文件内容算 SHA-256 指纹存进登记表，指纹没变就跳过。

2.重新入库某个文件前先 store.delete(where={"source": filename}) 清掉它的旧向量，否则同一文件的旧新版本会混在检索结果里

#### 2026-09-27　知识库 RAG · 第 6 阶段：检索评测（把"感觉还行"换成数字）

目标：前面几步的判断全靠"读一眼答案觉得对"。这一步建评测集，用指标决定 chunk_size 和 k，而不是拍脑袋。

先弄清原理：检索是 RAG 的地基——正确的段落没被召回，模型再强也答不出（它只能看到我们递给它的那几块）。所以这一步**只评检索、不评生成**：变量少、跑得快、还不用花钱调生成模型。四个指标各回答一个问题：

- Hit@K：前 K 块里"有没有"对的页（找没找到）
- Recall@K：该找到的页"找全了没有"（漏了多少）
- MRR：第一块对的证据排第几名（越靠前越好，喂进 prompt 的位置更前、更省 token）
- 关键词覆盖：检索回来的文本里含不含答案关键词（上下文够不够答题）

改动：

1.evals/questions.json（8 问）：每问带 expected_pages（0 起）和 expected_keywords。**期望页码不是猜的**——先写探测脚本真实跑一遍检索，看命中哪几页，再人工核对论文原文定下来

2.evals/metrics.py：四个纯函数 + evaluate() 汇总，不联网、不打模型，能被 pytest 完全覆盖

3.evals/retrieval_eval.py：chunk_size(500/1000/2000) × k(4/8) 网格实验，每组建一个独立的内存向量库（不碰 data/chroma 里的持久索引），结果写进 evals/results/{日期}-grid.{json,md}

4.按数据改配置：rag_chain.py 的 DEFAULT_K 从 4 改成 8，并加注释说明这个值来自网格实验

5.顺手修掉一个真 bug：Chroma 返回的 score 是**距离**（越小越相关），InMemoryVectorStore 返回的是**相似度**（越大越相关），两个后端同名不同义。api.py 换算成 `relevance = 1/(1+distance)` 落到 0~1，前端标签由"相似度"改成"相关度"

验证（物理证据）：

1.pytest evals → 8 passed / 0.04s（纯函数，离线免费）

2.pytest（apps/knowledge-rag）→ 27 passed, 5 skipped；test_api 的相关度断言同步改成 0.596

3.真实网格评测 6 组跑完（结论写在 evals/results/2026-09-27-grid.md）：k=8 在三组 chunk_size 下的 Hit@K / Recall@K 全面 ≥ k=4；chunk 1000 + k=8 三项指标 1.0 且只有 52 块 → 定为推荐默认

4.改完 k 重启服务，curl POST /kb/ask → HTTP 200，来源从 4 条变 8 条，页码 4/3/4/3/2/1/2/0、relevance 0.608→0.5 递减

踩坑：

1.页码口径：PyPDFLoader 的 metadata["page"] 从 **0** 开始。第一版 questions.json 我按"人翻 PDF 时看到的页码"写期望值，怎么算都不对。凡是可能有两套编号的地方（0 起 / 1 起），先探测再写断言，别凭直觉

2.建库耗时不能当性能指标：27 块那组测出 16.4s，同规模另一组只有 1.46s——差的是网络抖动。真实的成本代理是「块数」，它决定 embedding 调用次数和索引大小

3.样本太小就别过度解读：8 个问题意味着 1 个 case 就是 0.125 的差距，0.875 与 1.0 之间可能只差一道题。指标的作用是筛掉明显更差的配置，不是精调到小数点后三位

2.**负样本只能自己造，而且必须标注来源**：CMRC2018 公开的 dev / trial / test 三个 split 都没有原生 unanswerable 题。这 30 道是"问题来自真人标注、但其所属段落被排除在语料外"的构造式负样本（absent-context negatives），provenance 分别记 `cmrc2018_dev_human_annotated` 和 `constructed_absent_context`，不能含糊成"数据集原生就有不会答的题"。

3.**指标补 Precision@K、nDCG@K**（`evals/metrics.py`）：nDCG 按二值相关性算，位置 i 的折扣是 1/log2(i+1)，同一篇重复命中只在第一次计分；`evaluate()` 里没有 gold 时会抛错，负样本不进这条路径，单独统计。

4.**评测脚本** `evals/cmrc_retrieval_eval.py`：只给金标集建独立的内存索引，不进 `docs/`、不碰线上 Chroma；外层按 chunk_size 建库一次、内层只换 k（第一版写成每个 k 重建一次，等于同一批文本重复付 embedding）；除检索指标外还输出可回答题与负样本的 top1 相似度分布 + 阈值扫描。

验证（与证据）：

1.pytest：`evals` **24 passed**（原 8：+11 金标集构建用例、+5 precision/ndcg 用例），`apps/knowledge-rag` **38 passed, 5 skipped**。指标与抽取器全部离线跑，不打 API。

2.真实评测 4 组配置（chunk_size 0 / 500 × k 4 / 8，两个索引共 242 块、25 次 embedding 请求，建库 5.0s / 5.3s）：Hit@K、Recall@K、答案在上下文率**全是 1.0**；Precision@K 0.25 / 0.125，nDCG@K 0.994，MRR 0.993。结果在 `evals/results/2026-09-29-cmrc.{json,md}`。

3.真正有区分度的是相似度分布：可回答题 top1 相似度中位 0.7477（p25 0.6864、min 0.3912），构造负样本中位 0.3976（p75 0.4594、max 0.7885）。阈值扫描（chunk_size=0 组）：t=0.5 拒 24/30 负样本、误伤 3/200 可回答题；t=0.6 拒 27/30、误伤 19/200；t=0.7 拒 28/30、误伤 62/200。→ 这就是第 4 步阈值拒答的选点依据，不再是拍脑袋定距离阈值。

踩坑：

1.**CMRC 公开数据里有 27 道题的答案被 Excel 改坏了**：日期成了序列号（39764.0）、"147位"成了 147.0。抽取器第一次跑直接 `AttributeError: 'float' object has no attribute 'strip'`。可用的判据改成"每个答案必须是 str、且是原文里真实存在的字面 span"，含脏答案的段落整体排除（848 段里剩 683 段可用），数量记进 MANIFEST 的 `dirty_answer_items`。

2.**Precision@K 在单 gold 数据下天花板恒等于 1/K**：每题只有一个正确段落，k=4 时最高就是 0.25。我第一版把 0.25 / 0.125 读成"精度不行"，那其实是恒等式，不携带任何质量信息。要让 Precision 有意义，得换带 qrels（每题多个相关性分级）的数据集，比如 DuRetrieval。

3.**两组配置的指标一模一样，先怀疑脚本再下结论**：逐题比对发现 gold_rank 全同、但 200 道题里有 96 道的 top1 相似度不同、30 个负样本的分数也逐题不同——确认不是"k 没生效"的 bug，而是这份数据在检索层真的饱和了：100 段互不相干，干扰项太弱。结论要跟着改口：这份金标集**不能用来判 chunk_size 的优劣**，只能判"能不能找回来"和"查不到时能不能识别"。

4.**分数口径不能混**：`InMemoryVectorStore.similarity_search_with_score` 给的是余弦相似度（越大越相关），线上 kb-web 的 Chroma 给的是距离（越小越相关）。刚才扫出来的 0.5 这条线搬到 Chroma 上完全是另一回事，第 4 步做阈值拒答时得在线上那套口径下重扫一遍。

5.chunk_size=500 在中文段落上会切出碎尾块：142 块里有 7 块 ≤50 字、最短 33 字，overlap=0 时这种块基本没有上下文。上次"按句末下刀"解决的是切点自然，不解决短尾块——分块质量的判据得另加一条"块长分布"。
