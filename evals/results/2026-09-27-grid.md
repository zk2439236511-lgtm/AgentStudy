## 结论

上方表格由 `python evals/retrieval_eval.py` 自动生成（重跑会覆盖），下面这段是手写分析。

1. **k=8 全面优于 k=4**：三组 chunk_size 里，加大 k 只涨不跌。k=4 时 500/2000 两组 Hit@K 只有 0.875，说明有问题的正确页排在第 5~8 名被截断了。→ 已据此把 `rag_chain.py` 的 `DEFAULT_K` 从 4 改为 8。
2. **chunk=500 太碎**：块数 130（是 1000 的 2.5 倍），关键词覆盖却是全场最低（0.906）。句子被切开导致单块上下文不完整，embedding 调用也更贵。
3. **推荐默认 = chunk 1000 + k=8**：Hit@K / Recall@K / 关键词覆盖三项全 1.0，只有 52 块。
4. **chunk=2000 + k=8 的 MRR 略高（0.838 vs 0.76）**，但每块长度翻倍意味着同样 k=8 下喂进 prompt 的 token 大致翻倍。9 页样例文档无感，真实大文档不划算。
5. **`建库耗时` 别当性能指标**：16.4s 和 1.46s 的差异是网络抖动。真实成本代理是「块数」——它决定 embedding 调用次数和向量库大小。
6. **局限**：单文档、8 问、期望页码来自人工核对 + 真实检索探测。1 个 case 就是 1/8 = 0.125 的差距，所以 0.875 与 1.0 之间不要过度解读。要更硬的结论需扩到 30+ 问、多文档，并把 reranker 加入同一张网格对比。
